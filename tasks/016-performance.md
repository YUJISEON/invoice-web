## 지연·실패 시 최악 대기 시간 (로컬 목 서버, SDK `baseUrl`)

앱 코드에 테스트용 설정을 추가하지 않고 같은 SDK 설정으로 만든 `Client`를 `baseUrl`로 목 서버에 연결해 측정했다.

SDK 재시도 동작(실측): **429(`rate_limited`)만 재시도**하고(`Retry-After`만큼 대기), 500·503과 타임아웃은 재시도하지 않는다(쿼리는 POST라 비멱등).

| 상황                                      | 변경 전 (10초 / 3회 / 상한 60초) | 변경 후 (8초 / 2회 / 상한 2초) |
| ----------------------------------------- | -------------------------------- | ------------------------------ |
| 응답 없음(타임아웃)                       | 10.0초 후 오류                   | **8.0초** 후 오류              |
| 429, `Retry-After: 1` 계속                | 3.1초 (4회 요청)                 | 2.0초 (3회 요청)               |
| 429, `Retry-After` 없음                   | 6.5초                            | 1.2초                          |
| 429, `Retry-After: 5`                     | 15.0초                           | (미측정, 상한 2초라 약 4초)    |
| **429, `Retry-After: 20`**                | **60.1초** (재시도마다 20초)     | **4.0초**                      |
| 500·503 계속                              | 즉시 오류(재시도 없음)           | 즉시 오류(재시도 없음)         |
| 1초 지연 응답 × 호출 3개 순차             | -                                | 3.0초(성공)                    |
| 7.5초 지연(타임아웃 직전) × 호출 3개 순차 | -                                | 22.5초(성공, 이론적 최악)      |

핵심 발견: **SDK 기본 `maxRetryDelayMs`가 60초**라서 노션이 큰 `Retry-After`를 주면(예: 레이트 리밋이 걸린 상황) 정상 사용자가 빈 화면을 오래 보게 된다(20초 × 3 = 60초, 더 크면 이론상 수 분). 대기 상한을 2초로 제한해 실패하면 일반 오류 화면과 "다시 시도" 버튼으로 넘긴다. 이는 Task 015에서 평가한 "열거로 인한 가용성 저하" 위험도 줄인다.

## unstable_cache 도입 기준 (구현하지 않음, 문서화)

지금은 도입하지 않는다. 아래 중 하나가 생기면 도입을 검토한다.

- 같은 견적서에 대한 요청이 잦아 노션 평균 3 req/s 한도에 근접하거나 `rate_limited`가 서버 로그에 반복됨
- 응답 시간이 사용자가 체감할 만큼 커짐(예: 평균 2초 이상)

도입 시 조건: `unstable_cache`의 `revalidate`는 **60초 미만**(노션 수정이 1분 안에 반영되도록), 캐시 키에 토큰을 포함, 노션 파일 URL(약 1시간 만료)을 담지 않음(현재는 파일 속성을 읽지 않음), 오류 응답은 캐시하지 않음. 노션 수정을 즉시 반영해야 하는 운영 규칙과 충돌하므로 도입 전에 운영자와 합의한다.
