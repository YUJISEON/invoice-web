# 🧠 메타 프롬프트 — 노션 연동 견적서 MVP PRD 작성

> **이 문서의 용도**: 이 파일은 PRD 그 자체가 아니라, **PRD를 생성하기 위한 프롬프트**입니다.
> 아래 "메타 프롬프트" 섹션 전체를 복사해서 Claude Code에 붙여넣으면, `docs/PRD.md`에 MVP PRD 문서가 생성됩니다.

## 사용법

1. 아래 구분선 사이의 "메타 프롬프트" 전체를 복사
2. 새 대화 또는 현재 Claude Code 세션에 붙여넣기
3. Claude가 먼저 **확인 질문**을 던지면 답변 → 이후 `docs/PRD.md` 초안이 생성됨
4. 초안을 리뷰하며 수정 요청 (PRD는 1회성 생성물이 아니라 반복 수정 대상)

## ✂️ 메타 프롬프트 (여기부터 복사)

```
당신은 claude-nextjs-starters 기반 프로젝트(invoice-web)의 시니어 PM 겸 테크리드입니다.
아래 기능에 대한 MVP PRD 문서를 작성해주세요.

## 0. 작업 전 필수 확인
- `@/CLAUDE.md`를 읽고 이 프로젝트의 기술 스택(Next.js 15.5.3 App Router + Turbopack,
  React 19, TypeScript, TailwindCSS v4, shadcn/ui, React Hook Form + Zod + Server Actions)과
  문서 컨벤션을 파악하세요.
- `@/docs/guides/project-structure.md`, `@/docs/guides/styling-guide.md`,
  `@/docs/guides/component-patterns.md`, `@/docs/guides/forms-react-hook-form.md`를 훑어보고
  이 프로젝트의 문서 톤(한국어, 이모지 헤더, 코드블록 예시, 체크리스트)을 그대로 따르세요.
- `docs/PRD.md`가 이미 존재하면 먼저 읽고 기존 내용과 충돌하지 않게 보강하세요.
  존재하지 않으면 새로 작성하세요.

## 1. 기능 개요 (컨텍스트)
- 운영자(관리자)는 **노션(Notion)**에서 견적서 내용을 작성/관리합니다.
- 이 앱은 노션에 입력된 견적서 데이터를 가져와 **클라이언트(고객)가 웹앱에서 확인**할 수 있게 보여줍니다.
- 클라이언트는 확인한 견적서를 **PDF로 다운로드**할 수 있어야 합니다.
- 이것은 사내 도구가 아니라 **고객에게 노출되는 화면**이므로 신뢰감 있는 UI와 데이터 정확성이 중요합니다.

## 2. 먼저 질문할 것 (답변받기 전까지 PRD 본문 작성 금지)
PRD를 쓰기 전에, 아래 중 코드/기존 문서에서 확인되지 않는 항목은 반드시 사용자에게 먼저 질문하세요.
추측으로 채우지 마세요.

1. **노션 연동 방식**: Notion API(공식, Integration Token) 연동인지, 아니면 Notion
   "웹에 게시(Publish to web)" 링크를 임베드/스크래핑하는 방식인지?
2. **데이터 구조**: 노션 쪽 견적서가 DB(테이블)인지 개별 페이지인지, 필드 구성
   (상품/항목명, 수량, 단가, 세금, 합계, 유효기간, 고객사명 등)은 어떻게 되는지?
3. **클라이언트 접근 방식**: 로그인이 필요한지, 아니면 고유 링크(토큰 기반 URL)로
   비로그인 접근인지? (MVP 범위에 큰 영향)
4. **PDF 생성 방식 선호**: 브라우저 인쇄(CSS `@media print`), 서버 사이드 렌더링
   (예: `@react-pdf/renderer`, Puppeteer), 혹은 외부 서비스 중 선호가 있는지?
5. **노션 데이터 변경 반영 시점**: 실시간 동기화가 필요한지, 특정 시점에
   가져오기(fetch-on-view)로 충분한지?
6. **다건 지원 여부**: 클라이언트 1명이 여러 견적서를 볼 수 있어야 하는지,
   아니면 견적서 1건 = 전용 링크 1개로 충분한지?

질문에 대한 답변을 받으면, 이를 PRD의 "결정된 사항"으로 명시하고 본문을 작성하세요.
답변이 불확실한 항목은 PRD의 "Open Questions" 섹션에 남겨두고 임시 가정(assumption)을
명시한 뒤 진행하세요 (가정을 멈춤의 이유로 삼지 마세요).

## 3. PRD 문서 요구사항

파일 위치: `docs/PRD.md`
언어: 한국어, 기존 docs 톤(이모지 헤더 + 표 + 코드블록) 유지
형식: 아래 구조를 뼈대로 사용 (프로젝트 상황에 맞게 섹션 추가/조정 가능)

1. **개요 (Overview)** — 한 문단 요약, 누구를 위한 기능인지
2. **문제 정의 (Problem Statement)** — 현재 어떤 불편함을 해결하는지
3. **목표 / 성공 지표 (Goals & Success Metrics)** — MVP가 성공했다고 판단할 기준
4. **Non-Goals (이번 범위에서 명시적으로 제외하는 것)**
   — 예: 다중 통화, 전자서명, 온라인 결제 연동, 견적서 수정 기능(앱에서는 읽기 전용) 등
   모호하게 두지 말고 명시적으로 "하지 않음"을 나열
5. **사용자 시나리오 (User Stories)**
   - 운영자: "노션에 견적서를 작성하면, 고객에게 링크를 공유한다"
   - 클라이언트: "링크로 접속해 견적서를 확인하고, PDF로 저장한다"
6. **핵심 플로우 (Core Flow)** — 노션 입력 → 데이터 fetch → 앱 렌더링 → PDF 변환, 단계별 다이어그램 또는 순서 목록
7. **기능 요구사항 (Functional Requirements)** — 화면 단위로 쪼개서 구체적으로
   (예: 견적서 상세 화면에 표시되는 필드 목록, PDF 다운로드 버튼 동작, 에러/빈 상태 처리)
8. **기술적 고려사항 (Technical Considerations)**
   - 노션 API 연동 지점 (예: `src/lib/notion.ts` 등 이 프로젝트 구조 컨벤션에 맞는 위치 제안)
   - PDF 생성 방식과 트레이드오프 (품질/서버 부하/의존성)
   - 인증/접근 제어 방식
   - 에러 핸들링 (노션 API 실패, 견적서 없음, 만료된 링크 등)
9. **MVP 범위 (In Scope for v1)** vs **다음 단계 (Post-MVP / Nice to have)**
10. **오픈 이슈 (Open Questions)** — 미결정 사항과 임시 가정
11. **마일스톤 제안 (간단한 단계별 작업 순서)** — `docs/ROADMAP.md`가 있다면 그 톤에 맞춰 제안

## 4. 작성 원칙
- 추상적인 문장 대신 구체적인 화면/필드/동작 단위로 기술하세요.
- 이 프로젝트는 React Hook Form + Zod + Server Actions를 쓰는 컨벤션이 있으니,
  기능 요구사항에서 폼이 필요한 경우 이 패턴과 맞는지 고려해 언급하세요.
- 과도한 기술 설계(상세 아키텍처 문서화)는 PRD 범위가 아니므로 지양하고,
  "무엇을/왜"에 집중하고 "어떻게"는 구현 단계로 미루세요.
- 존재하지 않는 기능이나 아직 결정되지 않은 사항을 확정된 것처럼 서술하지 마세요.
```

## 📌 메타 프롬프트 설계 노트 (참고용, 복사 불필요)

- **질문을 먼저 던지게 한 이유**: 노션 연동 방식(API vs 퍼블리시 링크)과 인증 방식(로그인 vs 토큰 링크)은
  MVP 아키텍처를 완전히 다르게 만드는 결정이라, 가정만으로 PRD를 쓰면 다시 쓰게 될 위험이 큼.
- **Non-Goals 섹션을 강제한 이유**: "견적서 확인 + PDF 다운로드"는 범위가 쉽게 결제/전자서명/버전 관리까지
  번지는 기능이라, 명시적 제외 목록이 없으면 MVP가 아니라 풀스펙 제품 기획이 되어버림.
- **문서 위치를 `docs/PRD.md`로 고정한 이유**: `CLAUDE.md`가 이미 `@/docs/PRD.md`를
  "📋 프로젝트 요구사항" 문서로 가리키고 있어, 이 경로와 어긋나면 다른 가이드 문서들과
  참조 구조가 깨짐.
