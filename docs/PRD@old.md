# 📋 PRD: 노션 연동 견적서 클라이언트 확인 & PDF 다운로드 (MVP)

이 문서는 운영자가 노션(Notion)에 작성한 견적서를 클라이언트가 전용 링크로 접속해 확인하고,
PDF로 저장할 수 있게 하는 MVP 기능의 제품 요구사항을 정의합니다.

## ✅ 결정된 사항 (Decisions)

아래 4가지는 MVP 아키텍처를 좌우하는 핵심 결정으로, 사전 확인을 거쳐 확정했습니다.

| 항목                 | 결정                                                |
| -------------------- | --------------------------------------------------- |
| 노션 연동 방식       | **Notion API 공식 연동** (Integration Token 기반)   |
| 클라이언트 접근 방식 | **고유 토큰 링크, 비로그인** (`/quote/[token]`)     |
| PDF 생성 방식        | **브라우저 인쇄** (`@media print` CSS)              |
| 다건 지원 여부       | **견적서 1건 = 전용 링크 1개** (목록/대시보드 없음) |

## 1. 개요 (Overview)

운영자는 노션 데이터베이스에서 견적서를 작성·관리하고, 클라이언트는 운영자가 공유한 전용 링크로
접속해 견적서를 웹에서 확인한 뒤 PDF로 저장합니다. 이 화면은 고객에게 직접 노출되므로, 데이터
정확성과 신뢰감 있는 UI가 핵심입니다.

## 2. 문제 정의 (Problem Statement)

- 운영자는 노션에서 이미 견적서를 관리하고 있지만, 노션 페이지를 그대로 공유하면
  브랜딩이 없고 레이아웃이 통일되지 않아 고객에게 전문적으로 보이지 않습니다.
- 고객이 견적서를 저장/보관하려면 PDF가 필요한데, 노션 자체 내보내기는 포맷이 어색하고
  클라이언트가 직접 조작해야 합니다.
- 운영자가 견적서 작성 도구를 이중으로 관리(노션 + 별도 시스템)하지 않도록, 데이터 입력은
  계속 노션에서 하고 "보여주는 화면"만 이 앱이 담당합니다.

## 3. 목표 / 성공 지표 (Goals & Success Metrics)

- 운영자가 노션에 견적서를 작성한 뒤, 추가 수작업 없이 클라이언트에게 공유 가능한 링크를
  얻을 수 있다.
- 클라이언트가 링크 접속 후 5초 이내에 견적서 내용을 확인할 수 있다 (노션 API 응답 포함).
- 클라이언트가 별도 설치/로그인 없이 "PDF로 저장" 버튼(인쇄) 한 번으로 보관 가능한 결과물을
  얻는다.
- 견적서에 표시되는 금액/항목이 노션 원본과 100% 일치한다 (수동 재입력으로 인한 오차 없음).

## 4. Non-Goals (이번 범위에서 하지 않는 것)

- ❌ 앱에서 견적서를 **생성/수정**하는 기능 (작성은 항상 노션에서, 앱은 읽기 전용)
- ❌ 클라이언트 **로그인/회원가입**, 클라이언트별 견적서 목록·대시보드
- ❌ **전자서명**, 견적 승인/거절 액션
- ❌ **온라인 결제** 연동
- ❌ **다중 통화** 지원 (단일 통화, KRW 가정)
- ❌ 노션 ↔ 앱 간 **실시간(웹훅) 동기화** — 조회 시점 fetch로 충분
- ❌ 서버사이드 PDF 렌더링 (브라우저 인쇄로 대체)
- ❌ 링크 발급을 위한 운영자용 관리 UI (토큰 발급은 노션 속성값을 그대로 사용 — 아래 8절 참고)

## 5. 사용자 시나리오 (User Stories)

- **운영자**: "노션 데이터베이스에 견적서 행을 추가하고 고유 토큰 속성을 채우면, 그 값으로
  만들어진 링크를 고객에게 복사해서 보낼 수 있다."
- **클라이언트**: "받은 링크로 접속하면 로그인 없이 바로 견적서 내용(품목, 금액, 유효기간 등)을
  확인할 수 있고, 'PDF로 저장' 버튼을 누르면 인쇄 대화상자가 열려 PDF로 저장할 수 있다."
- **클라이언트 (예외)**: "링크가 잘못됐거나 만료된 견적서에 접속하면, 에러 상태 화면을 통해
  상황을 바로 이해할 수 있다."

## 6. 핵심 플로우 (Core Flow)

```
[노션 DB: 견적서 작성 + 토큰 속성 입력]
            ↓ (운영자가 링크 복사해 고객에게 전달)
[클라이언트: /quote/[token] 접속]
            ↓
[Server Component: Notion API로 토큰 매칭 레코드 조회]
            ↓
   ┌─ 조회 성공 ─────────────┐   ┌─ 조회 실패/만료 ─────────┐
   │ Zod로 응답 파싱·검증     │   │ 404 / 커스텀 에러 화면   │
   │ 견적서 상세 화면 렌더링  │   └───────────────────────┘
   └────────────┬────────────┘
                ↓
    [클라이언트: "PDF로 저장" 버튼 클릭]
                ↓
    [브라우저 print() 호출 → @media print 스타일 적용]
                ↓
         [클라이언트가 PDF로 저장]
```

## 7. 기능 요구사항 (Functional Requirements)

### 7.1 견적서 상세 화면 (`/quote/[token]`)

표시 항목 (노션 DB 속성 기준, 7.3 데이터 구조 참고):

- 상단: 발행 회사/로고(정적), 견적번호, 발행일, 유효기간
- 고객 정보: 고객사명, 담당자명
- 품목 테이블: 품목명, 수량, 단가, 금액 (행 단위 반복)
- 합계 영역: 소계, 부가세, 총액
- 비고/메모 (있을 경우만 노출, 없으면 섹션 자체 숨김)
- "PDF로 저장" 버튼 (화면 우상단, 인쇄 시 비노출 처리)

### 7.2 상태별 처리

| 상태                           | 동작                                                                                                  |
| ------------------------------ | ----------------------------------------------------------------------------------------------------- |
| 정상 조회                      | 견적서 상세 렌더링                                                                                    |
| 토큰에 해당하는 견적서 없음    | "유효하지 않은 링크입니다" 에러 화면, 404 상태                                                        |
| 유효기간 만료                  | "견적서 유효기간이 만료되었습니다" 안내 화면 (조회는 가능, 금액 비노출 또는 워터마크 — Open Question) |
| 노션 API 호출 실패/타임아웃    | "잠시 후 다시 시도해주세요" 에러 화면, 재시도 버튼                                                    |
| 필수 필드 누락 (Zod 파싱 실패) | 에러 로깅 후 일반 에러 화면 노출 (고객에게 내부 구조 노출 금지)                                       |

### 7.3 데이터 구조 (가정)

Notion 데이터베이스(견적서 DB) 속성 매핑 가정:

| Notion 속성 | 타입                           | 앱 내 필드                        |
| ----------- | ------------------------------ | --------------------------------- |
| 토큰        | Text (고유값)                  | `token` — URL 경로 매칭 키        |
| 견적번호    | Text                           | `quoteNumber`                     |
| 고객사명    | Text                           | `clientName`                      |
| 담당자명    | Text                           | `contactName`                     |
| 발행일      | Date                           | `issuedAt`                        |
| 유효기간    | Date                           | `expiresAt`                       |
| 품목        | Relation 또는 하위 테이블 블록 | `items[]` (품목명/수량/단가/금액) |
| 비고        | Text                           | `memo`                            |

> ⚠️ Notion DB 속성(Property)은 평평한(flat) 구조라 품목처럼 "행 안에 여러 줄"이 필요한
> 데이터는 기본 속성으로 표현하기 어렵습니다. 품목 리스트를 어떻게 모델링할지(연결된 하위 DB,
> 페이지 본문의 표 블록 파싱, 또는 JSON 문자열 속성)는 **8절 기술적 고려사항**과
> **10절 오픈 이슈**에서 다룹니다.

## 8. 기술적 고려사항 (Technical Considerations)

- **노션 연동 위치**: `src/lib/notion.ts`에 Notion API 클라이언트 초기화 및 조회 함수
  (`getQuoteByToken(token: string)`)를 둡니다. 프로젝트 구조 가이드의 `lib/` 확장 규칙을 따라
  `src/lib/schemas/quote.ts`에 Zod 스키마(`quoteSchema`)를 정의하고, Notion API 응답을
  그대로 신뢰하지 않고 파싱·검증합니다.
- **라우팅**: `src/app/quote/[token]/page.tsx` (동적 라우트, Server Component)에서 서버
  사이드로 노션 데이터를 조회합니다. 클라이언트에 Notion Integration Token이 노출되지
  않도록 반드시 서버 사이드에서만 API 호출.
- **PDF 생성**: 별도 라이브러리 없이 `window.print()` + 전역 CSS의 `@media print` 규칙으로
  처리합니다. 인쇄 시 버튼/네비게이션 등 UI 요소는 `print:hidden` 클래스로 숨김 처리
  (Tailwind `print:` 변형 활용).
- **인증/접근 제어**: 별도 로그인 없이 `token` 값 자체가 접근 제어 수단입니다. 토큰은
  추측 불가능한 충분한 길이의 랜덤 문자열이어야 하며(노션에서 수동 입력 시 생성 규칙 안내
  필요), URL에 평문으로 노출되는 점을 운영자에게 고지해야 합니다.
- **캐싱/동기화**: 실시간 동기화 대신 요청 시점 조회(fetch-on-view)로 처리하되, 노션 API
  레이트 리밋을 고려해 짧은 주기(예: Next.js `revalidate`)의 캐싱을 둘 수 있습니다. 다만
  과도한 캐싱은 "방금 수정한 견적서가 바로 반영되지 않는" 문제를 일으킬 수 있어 MVP에서는
  캐시 없이 매 요청 조회 → 이후 필요 시 조정하는 방향을 제안합니다.
- **폼 관련**: 이 기능은 읽기 전용 화면이라 React Hook Form이 필요한 사용자 입력 폼은 없습니다.
  다만 Notion API 응답 검증에는 프로젝트 컨벤션에 따라 Zod 스키마를 동일하게 재사용합니다.
- **에러 핸들링**: Notion API 실패는 `try/catch`로 감싸고, Next.js의 `notFound()` /
  `error.tsx`를 활용해 7.2의 상태표에 맞는 화면을 구성합니다.

## 9. MVP 범위 (In Scope) vs Post-MVP

**In Scope (v1)**

- 토큰 기반 견적서 상세 페이지 1종
- 노션 API로 견적서 1건 조회 + Zod 검증
- 품목/금액/고객정보 표시
- 브라우저 인쇄 기반 PDF 저장
- 조회 실패/만료/API 오류에 대한 기본 에러 화면

**Post-MVP (Nice to have)**

- 운영자용 링크 생성/토큰 관리 UI
- 견적서 유효기간 만료 시 자동 접근 차단
- 서버사이드 PDF 생성(디자인 고정, 인쇄 설정에 영향 안 받도록)
- 열람 여부/열람 시각 트래킹 (운영자 알림)
- 다건 조회(클라이언트 로그인 + 대시보드)
- 전자서명/승인 플로우

## 10. 오픈 이슈 (Open Questions)

| 이슈                                                                               | 임시 가정                                                        | 확인 필요 시점                                   |
| ---------------------------------------------------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------ |
| 품목(items) 리스트를 노션에서 어떤 구조로 표현할지 (연결 DB / 표 블록 / JSON 속성) | 연결된 하위 데이터베이스(Relation)로 가정, 8절 참고              | 구현 착수 전 운영자의 실제 노션 템플릿 확인 필요 |
| 토큰 생성 방식 (노션에서 수동 입력 vs 자동 생성 스크립트)                          | 운영자가 노션에서 랜덤 문자열을 수동 입력한다고 가정             | MVP 구현 전 결정                                 |
| 유효기간 만료 시 금액 비노출 여부                                                  | 만료되어도 조회는 가능하되 안내 배너만 추가 (금액은 그대로 노출) | 디자인 확정 전                                   |
| 노션 API 레이트 리밋 대응 (캐싱 여부)                                              | MVP는 캐싱 없이 매 요청 조회                                     | 트래픽 증가 시 재검토                            |
| 로고/브랜딩 자산 적용 방식 (정적 이미지 고정 vs 노션에서 가져오기)                 | 정적 이미지로 고정 (`public/` 자산)                              | 디자인 확정 전                                   |

## 11. 마일스톤 제안

1. **1단계 — 노션 연동 기반**: `src/lib/notion.ts` API 클라이언트, `src/lib/schemas/quote.ts`
   Zod 스키마, 토큰으로 단건 조회 함수 구현 (품목 구조는 오픈 이슈 확인 후 확정)
2. **2단계 — 견적서 상세 화면**: `src/app/quote/[token]/page.tsx` 라우트, 상태별(정상/에러/만료)
   UI 컴포넌트 구현 (`src/components/quote/` 하위)
3. **3단계 — PDF(인쇄) 대응**: `@media print` 전역 스타일, 인쇄 시 숨길 요소 처리,
   "PDF로 저장" 버튼 추가
4. **4단계 — 에러/엣지케이스 마감**: 노션 API 실패, 잘못된 토큰, 만료 처리 및 QA
5. **5단계 — 운영자 가이드 문서화**: 노션 템플릿에 토큰/링크를 채우는 방법을 운영자에게
   안내하는 짧은 가이드 작성 (Post-MVP 전환 전 임시 운영 매뉴얼)
